# 0. 地基结论：不要用加速度计算位移

**双重积分求位置在消费级手机上是不可行的。** 手机 IMU 的零偏典型值在 10–50 mg 量级，双积分后误差按 t² 增长：

| 时间 | 位置误差 |
|---|---|
| 1 s | ≈ 0.25 m |
| 5 s | ≈ 6 m |
| 10 s | ≈ 25 m |

一首 2 分钟的曲子，玩家的"绝对坐标"会漂到楼外面去。任何依赖 IMU 积分位移的判定都会在 10 秒内崩溃。

**可靠的只有两样：**

- **陀螺仪测姿态（旋转）** — 漂移约每分钟几度，且可用重力向量持续校正 pitch/roll
- **加速度计测瞬时冲量** — 短时窗内不积分，鲁棒

## 0.1 追踪方案三档

| 档位 | 技术 | 自由度 | 漂移 | 功耗 | 定位 |
|---|---|---|---|---|---|
| **A. 纯姿态** | 陀螺 + 重力融合 | 3DoF（旋转） | yaw 缓慢漂移 | 极低 | **首版核心与竞技基准** |
| **B. 视觉视差实验** | A + 肩关节模型或有界弹簧模型 | 3DoF + 派生视觉位移 | 无额外累计漂移 | 极低 | 可选表现层，不参与核心判定 |
| **C. 真 6DoF** | ARKit/ARCore VIO | 6DoF | 视觉丢失时可能跳变 | 高、发热 | 未来房间/AR 独立模式 |

## 0.2 B 档：可选的视觉视差实验

假设玩家手臂半伸、手机绕肩关节转动，那么手机位置就在一个半径 r ≈ 0.45–0.6 m 的球面上：

```
p_camera = q_device * (0, 0, -r) + shoulder_offset
```

只用姿态四元数可以派生一个**方向合理、且不会累计漂移**的视觉位移，但它并没有测量玩家的真实手机位置。

它可以补充**视差线索**：没有视差时，"音符的远近"在小屏幕上主要依赖缩放、遮挡和运动轨迹。加入小幅派生视差后，离散深度层会更容易辨认。

该效果必须满足三项约束：

- `r` 使用站姿/坐姿预设或舒适度设置，不尝试通过 IMU 反推真实臂长
- 位移被限制在很小的表现范围内，并可在前庭敏感设置中完全关闭
- 竞技判定仍只使用音符方向与呈现视角；视觉视差不得改变判定窗口或排行榜资格

## 0.3 不可妥协的架构约束

> **首版判定必须活在"角度空间"，不能依赖现实世界位移。**

谱面仍可以用三维舞台坐标描述音符；首版判定则由音符方向向量与玩家呈现视角的夹角决定。这样视觉位移误差、重定心和舒适度映射都不会破坏竞技公平性。

# 1. 空间：锚定、增益、边界、重定心

## 1.1 开局锚定

三步，全程 4 秒以内（音游玩家对开局摩擦极度敏感）：

1. **重力定 pitch/roll** — 加速度计静态读数直接给出，无需玩家配合，精度 ±1°
2. **玩家定 yaw** — `"举起手机，看向你想作为正前方的方向，长按 1.5 秒"` → 记录当前 yaw 为世界 0°
3. **选择姿态与幅度** — 站姿或坐姿，并按舒适设置确定角度笼与视角增益

> ⚠️ **绝对不要用磁力计定 yaw。** 室内磁场被钢筋、显示器、无线充电、手机自身扬声器磁体污染，误差 30–90° 是常态，且会在游玩中突变。宁可接受陀螺仪的缓慢相对漂移。

## 1.2 视角增益 G（被低估的核心参数）

手臂长度处的手机屏幕只占玩家真实视野的 20–25°，但游戏相机 FOV 通常设 60–75°。若做 1:1 映射，玩家要扫视一个 180° 的谱面就得真的转身，物理代价太高。

**增益系数 G**：物理旋转 Δθ → 虚拟视角旋转 G·Δθ

| G | 特性 |
|---|---|
| 1.0 | 真实、有空间感、可建立肌肉记忆，但活动量大 |
| **1.6–2.0** | **推荐默认**。物理 ±35° 覆盖虚拟 ±60–70°，手腕即可完成 |
| > 2.5 | 手抖被放大 2.5 倍，需显著加大判定窗和平滑。不推荐作为竞技档 |

**G 必须参与难度归一化。** 高增益 = 低体力消耗 + 高抖动敏感度。要么锁定竞技模式的 G，要么让判定窗随 G 自动补偿（`tolerance *= sqrt(G)`）并在排行榜标注。

## 1.3 边界与重定心

不要用物理围栏，用**角度笼**：yaw ∈ [-75°, +75°]，pitch ∈ [-50°, +55°]。

- **软边界表现** — 接近边界时屏幕边缘出现方向性辉光 + 轻微阻尼（超出部分按 `tanh` 压缩，永远不硬停），配合低频触感
- **隐形重定心** — 检测到玩家平均朝向持续偏离中心时，以 **0.4–1.2°/s** 的速率把世界缓缓拉回。该速率在人类视觉运动感知阈值之下，玩家察觉不到，但 3 分钟能修正 100° 以上的累积偏差。（VR 领域成熟技巧）
- **显式重定心** — 双指下滑手势，200ms 内平滑归位。兜底手段，也解决玩家中途换姿势的问题

## 1.4 姿态模式

首版原生支持站姿和坐姿：

| 模式 | 参考重力方向 | 角度笼 | 说明 |
|---|---|---|---|
| 站姿 | 竖直向下 | 全量 | 最佳空间感 |
| 坐姿 | 竖直向下 | pitch 上界收紧 | 默认 |

躺姿会改变重力参考轴、触控人体工学和设备跌落风险，暂列为后续无障碍研究项，不进入首版验收范围。底层坐标实现仍不应写死单一世界轴，以免阻塞后续扩展。

# 2. 操作：瞄准与触发必须分离

## 2.1 核心人机冲突

移动手机的手，和点击屏幕的手，是同一只手（或至少互相干扰）。**这是整个企划最大的人体工学风险。**

如果要求玩家"用手指精确点击音符在屏幕上的位置"，那么点击动作本身会带动手机抖动，破坏瞄准——瞄准和触发会互相污染。

## 2.2 解决方案：横屏双手混合操作

横持双手，双拇指常驻屏幕两侧：

```
┌──────────────────────────────────────────────┐
│  [左拇指区]                      [右拇指区]  │
│   粗略转向 / 直接点按              击发 / 长按 │
│   （按当前音符切换职责）            滑动 / 点按 │
│                                              │
│              ╭─────────╮                     │
│              │  准星区  │  ← 音符套进这里    │
│              ╰─────────╯                     │
└──────────────────────────────────────────────┘
```

- **手机姿态负责空间取景**，让玩家用手腕和前臂完成主要寻谱动作
- **中央捕获音符允许任一触发区点击**，不要求手指追着移动目标跑
- **直接点触音符只出现在双拇指安全区**，并避免与高速转向同时发生
- **左侧滑动可作为可选粗转向**，用于重定心、降低身体转幅或无障碍设置，不替代核心陀螺输入

## 2.3 混合交互与降级配置

捕获与直接点触不是两个互斥模式，而是同一谱面中的两种音符语法：

- 基础谱面约 70% 使用中央捕获，保证移动取景与节奏点击的稳定闭环
- 直接点触用于强调旋律、和弦和左右手编排；它必须遵守拇指可达性与角速度限制
- 长按、滑动与空间转向组成连续乐句，承担 3D 编舞的主要表现力
- 固定视角配置关闭陀螺并将谱面投影为 2D，仅作为通勤与无障碍降级，成绩单独标记

## 2.4 音符类型

传统音游只有"点/长按/滑"三种。这套输入系统能做的更多：

| 类型 | 交互 | 可靠性 | 备注 |
|---|---|---|---|
| **Pulse（捕获点）** | 套进捕获区 + 任一触发区点击 | ★★★★★ | 首版基础音符 |
| **Point（直触点）** | 直接点击音符的屏幕投影 | ★★★★☆ | 命中区随角速度适度放宽 |
| **Rail（轨迹长音）** | 按住并保持音符在捕获区，沿三维曲线转动手机 | ★★★★★ | 首版特色音符 |
| **Sweep（扫光）** | 按住并用手机扫过一串弧线音符 | ★★★★★ | Rail 的高表现力变体 |
| **Slice（切向）** | 捕获后按屏幕提示方向滑动 | ★★★★☆ | 触屏方向承担节奏重音 |
| **Steady（稳持）** | 长音期间保持手机稳定，角速度影响空间表现分 | ★★★★☆ | 后续扩展，避免惩罚自然手抖 |
| **Thrust（推/拉）** | 用加速度短时冲量识别推拉动作 | ★★★★☆ | 后续扩展；200ms 窗口，不积分 |
| **Flick / Snap** | 腕部翻转或快速转向指定方位 | ★★★☆☆ | 高疲劳，仅在高难谱中节制使用 |

首个可玩原型只实现 **Pulse、Point、Rail**。Steady、Thrust 等机制必须在基础节奏闭环成立后再验证，不能用新奇动作掩盖核心手感问题。

# 3. 阻尼、抖动，与"所见即所判"

## 3.1 常见的错误做法

给姿态加一个统一的低通滤波 → 画面稳了，但：
- 判定延迟增加 30–60ms
- **玩家看到的位置和系统判定的位置不一致**，产生"我明明对准了却 Miss"的挫败

这种不公平感会直接杀死一款音游。

## 3.2 正确架构：所见即所判 + 双路径 + 时间戳回溯

```
IMU 回调（100–500 Hz，带硬件时间戳）
        │
        ├─→ 原始姿态历史（诊断 / 追踪质量 / 预测输入）
        │
        └─→ One Euro Filter → 预测外推 → 呈现姿态
                                           ├─→ 相机
                                           └─→ PresentedPoseHistory

触摸事件（携带 OS 时间戳 t_touch）
        │
        └─→ 映射到呈现时间轴 → 取出当时的【呈现姿态】→ 空间判定
```

> **关键：空间判定使用玩家触摸时实际看到的呈现姿态。** 滤波、预测和视角增益后的姿态必须带呈现时间戳写入 `PresentedPoseHistory`，再按触摸事件回溯。

原始姿态历史仍用于传感器诊断、追踪质量评估和预测，但不能直接作为玩家不可见的第二套瞄准事实。滤波也不能无限加重：它虽然不会造成"画面和判定不一致"，但仍会让操控显得黏滞。

iOS 的 `UITouch.timestamp` 和 Android 的 `MotionEvent.getEventTime()` 都提供了这个时间戳。**不要用 `Time.time`。**

## 3.3 One Euro Filter：自适应阻尼

固定截止频率的低通滤波是错的——静止时平滑不够（抖），运动时延迟太大（黏）。One Euro Filter 的截止频率随速度自适应：

```
慢速/静止 → 低截止频率 → 强平滑 → 消除手抖
快速转动 → 高截止频率 → 弱平滑 → 低延迟跟手
```

推荐起始参数（需按机型和 G 值调优）：

| 参数 | 建议值 | 含义 |
|---|---|---|
| `mincutoff` | 1.0–1.5 Hz | 静止时的平滑强度 |
| `beta` | 0.01–0.05 | 速度自适应强度 |
| `dcutoff` | 1.0 Hz | 导数滤波截止 |

对 pitch / yaw / roll 分别调参。roll 可以更重（roll 抖动对可玩性影响最小，但视觉上最晕）。

## 3.4 补充的抗抖手段

- **软死区** — 角度 0.15–0.3° 以内按平方衰减。不要硬死区，硬死区会产生"粘滞—跳脱"的顿挫感
- **姿态预测外推** — 用当前角速度线性外推 15–25ms，抵消渲染管线延迟。VR late-latching 的简化版，收益明显、风险低。超过 30ms 会在急停时产生过冲
- **辅助瞄准（Aim Assist）** — 判定锥在音符临近判定时刻的 ±80ms 内动态扩大 30–50%。**这不是作弊，是必需的可用性设计**，且比任何滤波都更有效地解决手抖问题，同时不引入延迟
- **视觉锚定补偿** — 让音符在最后 100ms 内做亚像素级的轻微跟随（磁吸感）。慎用，量要极小，过量会产生"音符在躲我"的诡异感

> **分层原则：能用判定容差解决的，不要用滤波解决；能用滤波解决的，不要用延迟解决。**

# 4. 延迟预算与时钟架构

## 4.1 端到端延迟拆解

| 环节 | 典型值 | 可优化空间 |
|---|---|---|
| 触摸采样（60–240 Hz 面板） | 4–16 ms | 选高刷设备 |
| 触摸事件传递到应用 | 5–15 ms | 时间戳回溯可消除影响 |
| 游戏逻辑帧 | 8–16 ms | 提高帧率 |
| 渲染 + GPU | 8–16 ms | 简化管线 |
| 合成器 + 垂直同步 | 16–33 ms | 控制呈现队列深度，优先平台低延迟路径 |
| 面板扫描输出 | 5–10 ms | 无 |
| **视觉总计** | **45–105 ms** | |
| 音频输出（Android AudioTrack） | 40–200 ms | **必须走 AAudio / Oboe 低延迟路径 → 10–40 ms** |
| 音频输出（iOS AVAudioEngine） | 10–25 ms | 已经很好 |
| 蓝牙耳机附加延迟 | **120–250 ms** | 不可优化，只能校准 |

## 4.2 时钟架构

> **音频 DSP 时钟是唯一主时钟。**

所有音符时间、判定窗口、动画进度都从 `AudioSettings.dspTime`（或平台等价物）派生，**绝不使用 `Time.time` 或帧计数**。帧率抖动不能影响节奏。

## 4.3 三项独立校准（不能合并成一个滑块）

1. **音频偏移** — 纯听觉，节拍器对拍
2. **显示偏移** — 纯视觉，光标撞线
3. **触控偏移** — 设备自身触摸采样延迟

三者必须分开测：蓝牙耳机只影响第 1 项，高刷屏只影响第 2 项。合并成一个"整体偏移"是常见的偷懒做法，会导致换耳机后校准全废。

**再加一个自动校准**：游玩前 30 秒的判定偏差做直方图统计，若均值稳定偏移 > 15ms，提示玩家一键采纳。

## 4.4 判定计算的性能

不要用 3D 物理射线检测。判定就是一次点积：

```
cos(θ) = dot(normalize(note_direction), camera_forward)
命中 ⟺ cos(θ) > cos(tolerance_angle)
```

配合时间窗预筛，任一时刻的候选音符数是个位数。整个判定系统应在 **0.05 ms** 以内完成。

# 5. 判定模型

## 5.1 二维判定：时间 × 空间

**时间评级**

| 评级 | 窗口 |
|---|---|
| Perfect | ±35 ms |
| Great | ±70 ms |
| Good | ±110 ms |
| Miss | 超出 |

**空间容差**

| 项 | 角度（Normal 难度基准） |
|---|---|
| 基础判定锥 | 半角 4.5° |
| 临近时刻辅助扩大 | → 6.5° |
| 高难度收紧 | 3.0° |

## 5.2 空间门槛二元，空间表现连续

> **是否激活是二元条件；激活后的对准质量形成空间表现分，节奏评级仍完全由时间偏差决定。**

这样既能保证失误可归因，又能奖励更准确、流畅的空间操作：

- **没进入宽松激活锥** = 空间失败（`Out of Frame`），不进入时间评级
- **已激活但时间偏差较大** = 节奏问题，按 Perfect / Great / Good 反馈
- **已激活且更接近捕获中心** = 获得更高空间表现分，但不把 Great 改名成另一套混合评级
- 音符激活后保留约 120ms 的滞回，避免自然手抖在拍点前造成反复锁定/脱锁

默认总分建议为：

```text
TotalScore = RhythmScore * 0.8 + SpatialPerformance * 0.2
```

其中连击与主要评级由 `RhythmScore` 驱动；`SpatialPerformance` 根据捕获中心偏差、Rail 跟随稳定度和动作连贯性计算。臂展 3DoF、固定视角和未来房间 6DoF 必须分别记录与排行。

## 5.3 反馈设计

视线在移动中，玩家很可能看不到判定文字。因此：

- **音频反馈是主要即时通道** — 击打音效与判定精度绑定（Perfect 音色清亮，Good 略闷），并由 DSP 时钟调度
- **视觉** — 径向冲击波从判定点扩散到全屏边缘，即使不看中心也能感知
- **触感（Haptics）是辅助通道** — Perfect / Great / Miss 可使用不同波形，但设备差异和触感延迟使其不适合作为唯一节拍依据

# 6. 谱面设计方法论

> 3D 音游最难的部分——**空间里的音符如果玩家找不到，谱面就等于不存在。**

## 6.1 核心指标：注意力锥与角速度预算

谱面工具必须实时显示这两个量：

### （1）所需角速度 `ω_required = Δangle / Δt`

| 区间 | 分级 |
|---|---|
| < 60°/s | 舒适（手腕） |
| 60–150°/s | 可接受（前臂） |
| 150–300°/s | 高难（全臂/转身） |
| > 350°/s | **不可能** → 编辑器直接报错 |

### （2）预告时间（从进入可视锥到判定时刻）

| 场景 | 最低要求 |
|---|---|
| 屏外音符 | **≥ 800 ms**（含引导指示） |
| 屏内音符 | ≥ 400 ms |

违反 → 编辑器警告"偷袭音符"。

## 6.2 可读性三件套

音符**钉在自己的固定坐标上原地生成**（从小长到实际大小），不会飞向玩家。让音符自己送到眼前会毁掉"寻找"这件事——而主动转动设备去发现音符，恰恰是这套输入方式唯一不可替代的乐趣。所以引导的对象是**路径**，不是音符本身。

1. **屏外指示器** — 屏幕边缘的方向箭头 + 距离条，提前 1.2 s 出现
2. **引导线（视线编舞曲线的可见化）** — 一条贴在球面上、穿过后续音符的弧线，加一个按主时钟沿线前进的光点。玩家的任务是"用准星跟住光点"，音符会在他到达时正好长到实际大小。**最有效的引导手段**
3. **空间音频（HRTF）** — 戴耳机时，音符的预告音从其真实方位传来。**这一条把"寻找音符"从视觉负担变成了听觉本能**，也让"这是个音游"在机制层面成立。强烈建议作为核心功能而非附加项

## 6.3 分区编舞（Zoning）

不要让音符随机散布在球面上。把空间切成 5–7 个**扇区**（正前、左、右、上、下、左下、右下），**一个乐句 = 一个扇区**。

段落切换时用强引导（光带扫过、扇区高亮、鼓点重音 + 触感脉冲）把玩家的视线牵过去。

这样谱面就有了 **音乐结构 = 空间结构** 的对应关系。玩家记住的不是"音符在哪"，而是"副歌在右上方"。这是可记忆、可练习的。

## 6.4 乐器—方位映射

让方位承载音乐语义：

| 声部 | 方位 |
|---|---|
| 鼓组 | 下方（踩地感） |
| 主旋律 | 正前 |
| 和声/铺底 | 两侧 |
| 高频装饰音（hi-hat、铃） | 上方 |
| Bass | 正前偏下、近距离（大而近） |

配合空间音频，玩家转向某个方位时该声部的音量自然提升——**玩法动作与听觉体验合一**。这是本企划在美学上最有说服力的点。

## 6.5 体力曲线（VR 血泪教训）

举着手机扫视是**有氧运动**。参考 VR 的"猩猩臂"问题：

- 首批曲目以 **90–180 秒**为主；超过 3 分钟的歌曲必须安排更多低强度与放松段落
- 高强度扫视段落 ≤ 40 秒，之后必须接低强度段落
- **静止段作为正式设计元素** — 音乐安静时让玩家把手机放平/举高看星空，只有稀疏的 Steady 音符。既是休息，也是情绪对比，还是叙事窗口
- 手机重量 180–240 g，单手长时间举起在 3 分钟后就会明显不适。**这是硬约束**

## 6.6 遮挡与深度

- 近处音符不能遮挡远处音符的可读性 → 编辑器需做**视锥遮挡检测**
- 深度差应 ≥ 1.5 倍才能被可靠感知，并同时使用缩放、遮挡、运动轨迹及可选视觉视差
- 建议只用 **2–3 个离散深度层**（近/中/远），而非连续深度。连续深度在小屏幕上读不出来

# 7. 谱面编辑器

> **这是最容易被低估的工作量，也是项目成败的关键。**
> 一个 3D 音游如果编辑器难用，就永远做不出足够多的好谱面，游戏也就没有内容。

## 7.1 坐标系：标准化三维存储，球坐标创作

谱面文件使用 `PlayVolume` 内的标准化三维坐标作为唯一存储事实；编辑器默认将其显示为 `(方位角 azimuth, 仰角 elevation, 深度层 depth)`。

**理由**：谱师的操作本质是"编排玩家转向"，球坐标更符合创作思维，也天然对应角速度预算；标准化三维存储则能让同一谱面未来映射到臂展椭球体或房间安全体积，而不把具体米制尺寸写死在谱面中。

## 7.2 分层架构：先编舞，后布点

```
第 1 层：视线编舞曲线（Gaze Choreography Curve）
   作者画一条"玩家视线随时间应该走的路径"
   ↓
第 2 层：音符吸附
   音符以【相对编舞曲线的偏移量】定义，而非绝对坐标
   ↓
第 3 层：装饰与特效
```

**这是最重要的架构决策。** 它同时是**玩家可见的游戏元素**——运行时以引导线的形式呈现（见 §6.2），所以作者画的曲线就是玩家真正要走的路径，编辑器所见即玩家所得。好处：

- 可玩性天然有保障（音符永远在视线附近）
- 全局调整极其高效（改一条曲线 = 重排整段谱面）
- 角速度预算直接从曲线本身算出，实时可视化
- 难度变体（Easy/Hard）可共用编舞曲线，只改偏移量和密度

## 7.3 设备联动 + 手势录制（杀手锏工作流）

**3D 谱面的手感在 PC 上用鼠标是验证不了的。** 必须做：

- **PC ↔ 手机实时同步** — PC 端做时间轴、批量操作、精确数值；手机作为实时取景器，作者随时举起手机检查"这段扫视舒不舒服"
- **手势录制打谱（Motion Capture Charting）** — 作者举着手机跟着音乐挥动，系统同时记录：
  1. 姿态轨迹 → 自动生成编舞曲线
  2. 敲击时刻 → 自动生成音符

  然后在 PC 上量化、吸附到节拍网格、精修

这个工作流会把打谱效率提升一个数量级，且天然保证人体工学的合理性（因为它是真人做出来的动作）。它也是 UGC 的基础：普通玩家不会用时间轴，但会跟着音乐挥手机。

## 7.4 Lint 规则清单（必做）

编辑器应像代码 Linter 一样实时标红：

- [ ] 角速度超限（分档警告 / 报错）
- [ ] 屏外偷袭（预告 < 800ms）
- [ ] 音符视锥遮挡
- [ ] 判定锥重叠（两音符角距 < 2× 判定容差 → 误判风险）
- [ ] 超出角度笼边界
- [ ] 拇指可达性（Point 音符落在双拇指安全区之外）
- [ ] 体力曲线过载（滑动窗口内累积角位移超阈值）
- [ ] 手性偏置（谱面是否过度偏向右侧，对左撇子不公平）

## 7.5 Replay 系统

存储 `(呈现姿态流 + 触摸事件流 + 校准参数 + 追踪模式)`，可完整重放；原始传感器流仅在获得调试授权时附加保存。三个用途：

1. **调试** — 作者看真人游玩录像，定位"大家都在这里 Miss"的地方。配合**失败热力图**：把所有玩家的 Miss 点投影到球面上
2. **反作弊** — 服务端验算
3. **社交** — 观看别人的 replay 就像看一段舞蹈。这个玩法的 replay 天然好看，因为它记录的是人的动作，不是按键序列

## 7.6 核心数据与追踪接口

以下是概念层契约，具体字段类型与 JSON Schema 在原型阶段定稿：

```text
Chart {
  TempoMap
  PlayVolume
  Phrase[]
  NoteEvent[]
  StageEvent[]
  TrackingModeCertification[]
}

NoteEvent {
  beat
  noteType
  normalizedPosition
  approachCurve
  previewBeats
  interactionProfile
  scoringProfile
  optionalModeOverride
}

PoseSample {
  sensorTimestamp
  rotation
  optionalPosition
  trackingQuality
}

ITrackingProvider.Sample(timestamp) -> PoseSample
PresentedPoseHistory.SampleAt(presentationTimestamp) -> PoseSample
CoordinateMapper.Map(stagePoint, calibration, playMode) -> runtimePoint
```

- 首版只实现 `Rotation3DoFProvider`；`optionalPosition` 为空，或仅承载不参与判定的有界视觉视差
- 未来 `AR6DoFProvider` 可以提供真实位置，但必须通过相同接口输出，并由模式认证决定谱面与排行榜资格
- `CoordinateMapper` 负责定锚、重定心、视角增益和活动空间映射，不能让谱面逻辑直接读取平台传感器

# 8. 性能与发热

> 音游对**帧率稳定性**的要求远高于峰值帧率。一次 100ms 的卡顿就是一个 Miss。

- **目标** — 稳定 120 fps（支持设备）/ 稳定 60 fps。宁可锁 60 也不要在 60–90 之间跳动
- **音符渲染** — GPU Instancing，一个 Mesh + MaterialPropertyBlock。绝不给每个音符一个 GameObject（上千个 Transform 更新会吃掉主线程）
- **位置计算** — Job System + Burst，SIMD 批量算球坐标到世界坐标的转换
- **后处理克制** — Bloom 走 1/4 分辨率；关闭实时阴影（用烘焙或假阴影）；不要 SSAO / SSR
- **热管理** — 移动端音游的隐形杀手。持续高负载 10–15 分钟后 SoC 降频 → 掉帧 → 判定手感崩坏：
  - 内置**温度监控**，检测到降频时主动降低画质档位（而不是让帧率掉下去）
  - 选曲界面、结算界面主动降帧到 30 fps 散热

> 这一条直接决定了 AR 模式的可行性。

# 9. 未来 6DoF 与 AR 路线

## 9.1 当前版本边界

首版 3DoF 模式**不申请、不调用摄像头**，也不在后台启动 ARKit/ARCore。当前活动范围是原地臂展，不提供房间级位置判定。

即使只使用 VIO 位姿而不显示实景画面，系统仍然需要摄像头参与追踪并要求用户授权。因此所谓 AR-lite 也属于未来摄像头模式，不能包装成当前的无摄像头能力。

## 9.2 真实 6DoF 的收益与代价

| 收益 | 代价 |
|---|---|
| 真实位置、视差与空间尺度 | 持续摄像头和 VIO 计算显著增加功耗、发热与降频风险 |
| 可围绕音符观察和真实走位 | 依赖环境纹理与光照；追踪丢失或重定位会造成坐标跳变 |
| 实景录屏和传播性 | 增加摄像头权限顾虑，真实背景也会降低音符可读性 |
| 房间互动和共享锚点 | 需要边界扫描、安全提示、多人同步与更复杂的谱面验证 |

追踪质量下降时不能在一首竞技歌曲中悄悄切换为伪 6DoF，因为坐标语义会发生变化。正确处理是暂停、提示重新定位，并将无法恢复的该局标记为未认证成绩。

## 9.3 房间模式的安全与公平边界

- 开局扫描或确认安全活动区域，将可玩体积向内收缩至少 0.4m 后再放置音符
- 谱面不得要求玩家盲目后退、跨越障碍物或高速转身后立即移动
- 玩家接近边界、VIO 质量下降、光照不足或锚点突变时立即给出可见提示，必要时自动暂停
- 臂展 3DoF 与房间 6DoF 共享歌曲和谱面语义，但使用独立模式认证、判定参数、成绩记录与排行榜
- 摄像头权限按需申请；进入模式前明确说明用途、功耗和环境要求，拒绝授权后仍可完整使用 3DoF 核心模式

## 9.4 分阶段路线

| 阶段 | 内容 |
|---|---|
| **V1** | 无摄像头 3DoF 臂展模式；Pulse、Point、Rail 和基础编辑器 |
| **V1.x 实验** | 可关闭的肩关节/弹簧视觉视差；不改变核心判定与排行榜资格 |
| **6DoF 技术验证** | 独立分支通过 AR Foundation 测试 ARKit/ARCore 追踪、发热、重定位与房间边界，不进入首版产品 |
| **V2** | 用户主动授权的房间 6DoF 模式，使用独立认证谱面和排行榜；可先保留纯虚拟背景 |
| **V3** | 实景 passthrough 表演模式、现实遮挡和录屏分享，不作为核心竞技入口 |
| **V4** | 共享锚点、同场协作谱面及多人安全机制 |

AR 真正不可替代的长期价值在于**真实空间关系与同场协作**，而不只是把虚拟背景替换成摄像头画面。

# 10. 思维发散

## 10.1 机制层

- **手机即乐器** — Steady 音符可以把稳定控制转化为可选空间表现分：弦乐长音期间保持目标在宽松区域内，稳定度映射为音色层次。它不能要求"绝对静止"，也不能惩罚玩家不可控的自然手抖
- **扫光乐句（Sweep）** — 一串音符沿弧线排布，玩家按住屏幕用手机"扫"过去。视觉上像用手电筒扫过一串灯，适合作为副歌高潮
- **深度对焦** — 用 Thrust（推拉冲量）切换焦平面。近层音符和远层音符交替出现，玩家需推拉手机"对焦"。这给了深度维度真正的玩法意义
- **反向机制：躲避** — 某些"噪音"物体需要**避免**让它进入准星。把"瞄准"和"避让"混合，创造张力
- **重力谱面** — 音符受虚拟重力下坠，玩家需在它们落到底部之前接住

## 10.2 主题与美学

这个玩法天然适合"环视"型题材：

| 主题 | 说明 |
|---|---|
| **星空/星座** ⭐ | 谱面轨迹 = 星座连线，完成一曲 = 点亮一个星座。契合度极高，视觉成本低（黑底 + 发光点） |
| 深海 | 生物从各个方向游过，深度感强 |
| 都市霓虹 | 赛博朋克，天生适合手机取景框的隐喻 |
| 脑内空间 / 记忆宫殿 | 叙事潜力大 |

> **星空方案是首选** —— 同时解决了美术成本、可读性（高对比度）、和主题契合度三个问题。

## 10.3 社交与 UGC

- **手势录制打谱** → 普通玩家也能产出谱面
- **Replay 即舞蹈** — 分享的不是分数截图，而是"你的身体在空间中划出的轨迹"。把姿态轨迹渲染成一条光带，作为可分享的视觉资产
- **轨迹指纹** — 每个玩家打同一首曲子的姿态轨迹都不同，这是独一无二的"演奏风格"。可做"跟随大师轨迹"的教学模式（半透明目标轨迹叠加在你的轨迹上）
- **异步对战** — 对手的轨迹以幽灵形式显示在你的空间里

## 10.4 无障碍（同时也是市场扩张）

必做项，成本不高但受众收益巨大：

- **降幅模式** — 整个球面压缩到 ±25°，坐着微动手腕即可完成
- **固定视角模式** — 完全关闭陀螺仪，退化为传统 2D 音游。**这不是慈善，是必需品**：在颠簸的地铁上，陀螺仪玩法完全不可用
- **单手模式** — 所有触发合并到一个区域
- **判定窗放宽档位**（与排行榜分离）
- **色盲友好** — 不用颜色作为唯一区分维度
- **前庭敏感** — 关闭相机加速/减速动画，减少视觉流

# 11. 风险清单与原型验证路线

按"能杀死项目的程度"排序。前三项任一不过，玩法根基就不成立，**应该在写任何正式代码之前用灰盒 demo 验证**。

## P0：三天内必须验证（灰盒原型）

| # | 风险 | 验证方法 | 通过标准 |
|---|---|---|---|
| 1 | **手臂疲劳** | 随机音符灰盒，找 10 人连续玩 5 分钟 | 5 分钟后无明显不适，愿意再来一局 |

# 13. 三条不可妥协的原则

> **1. 判定活在角度空间里。**
> 任何位移追踪的误差、漂移、重定心都不能影响公平性。

> **2. 所见即所判。**
> 空间判定使用玩家实际看到的呈现姿态，从带呈现时间戳的历史中回溯取出。滤波必须兼顾稳定与跟手，不能另用一套不可见的原始姿态判定。

> **3. 音频 DSP 时钟是唯一主时钟。**
> 帧率抖动不能污染节奏。

这三条定下来，剩下的都是可以迭代调优的参数。反过来，这三条里任何一条做错，后期都需要重写核心系统。
